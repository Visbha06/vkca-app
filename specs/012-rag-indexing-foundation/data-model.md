# RAG Indexing Foundation Data Model

Feature: 012-rag-indexing-foundation  
Storage: PostgreSQL 16 with pgvector  
Migration: 014_rag_indexing_foundation after current head 013

## Modeling Principles

- Relational academy tables remain authoritative. RAG rows are disposable,
  rebuildable derived state.
- A registered source has a deterministic source_type and source_key. Normal
  entity keys use the source UUID; Calendar keys use the stable
  CalendarEventInstance.occurrence_id.
- A canonical document ID is deterministic from source type and source key,
  independent of the current embedding provider. A chunk ID is deterministic
  from its document ID and ordinal.
- The active document/chunk set is replaced only after a complete candidate has
  valid embeddings. A failed eligible refresh retains the prior active set.
- Authorization facets describe source relationships. They never contain
  authorized User IDs or role snapshots.

## In-Memory Contracts

### CanonicalRagDocument

A builder output with:

- deterministic document ID, source type, source key/entity ID;
- authoritative source version and dependency fingerprint;
- normalized semantic text and content hash;
- structured provenance;
- RagScopeMetadata;
- builder/schema version;
- preparation timestamp.

It is created by a source builder and contains no SQLAlchemy session, provider
client, vector, or retrieval query.

### RagScopeMetadata

The intrinsic facet used to build query predicates:

- source type;
- Player IDs;
- Team IDs;
- age groups;
- all-academy flag;
- optional source-specific relationship labels needed for provenance.

No role, User ID, or current assignment snapshot is stored.

### RagChunkCandidate

A deterministic chunk with parent document ID, ordinal, text/hash,
provenance/scope facets, builder/chunking versions, and no embedding until the
provider returns a validated vector.

### RagAccessScope

A request-time authorization projection:

- authenticated database User ID internally, never persisted in result metadata;
- current UserRole;
- active account state;
- linked active Player ID or null;
- current Team IDs from TeamCoach or TeamPlayer;
- current Team age groups;
- active Player IDs currently in assigned Teams for Assistant Coaches;
- is_unlinked_player;
- can_read_all_registered_sources.

The resolver is the only component that derives this from current
relationships. Callers cannot construct it from request fields.

## Authorization Query Rules

The retrieval query must first constrain searchable chunks by current scope,
then order the remaining candidates by cosine distance and apply the configured
result limit.

- Head Coach: is_searchable = true and all registered source types.
- Assistant Coach: assigned Team facets, active Players in those Teams, related
  Match/performance/statistics/Team facets, plus all-academy or assigned-age-group
  Calendar facets. Inactive Players and unrelated Teams are excluded.
- Linked Player: own Player facet, current Team facets, related Matches and
  Calendar facets. No unrelated Player facet is allowed.
- Unlinked Player: return zero Player/team-specific candidates with no
  academy-wide fallback.
- Inactive User or linked inactive Player: authentication prevents entry to the
  retrieval service.

The SQL predicate must be expressed in the database candidate query. It must not
retrieve a broad vector candidate set and filter forbidden chunks in Python.

## State Transitions

### Source state

- current -> pending when source/dependency/builder/model state changes.
- pending -> indexing when a run claims the source.
- indexing -> current only after the complete candidate is activated.
- indexing -> failed when embedding or persistence fails; retain active rows if
  the source remains eligible.
- failed -> indexing on a later repair/incremental run.
- Any eligible state -> ineligible or deleted when source eligibility is lost
  or the source disappears; deactivate/remove searchable rows.
- Any state -> stale when source truth is newer than the last active version or
  when a model compatibility check fails.

### Run state

- indexing -> completed when all selected sources reconcile successfully.
- indexing -> partial when some sources fail but the run remains recoverable.
- indexing -> failed when setup, compatibility, or global provider failure
  prevents useful reconciliation.
- A repair run can claim stale/failed sources without rebuilding unrelated
  current source types.

## Database Indexes and Constraints

The migration should create:

- unique source identity and document identity constraints;
- B-tree indexes on source type/key, source status, model/dimension, active state,
  and last-attempt timestamps;
- GIN indexes on player_ids, team_ids, and age_groups;
- a cosine HNSW index on rag_chunks.embedding using vector_cosine_ops;
- foreign keys from source state/document/chunk rows with safe cascade behavior;
- check constraints for valid statuses, non-negative counters, positive dimensions,
  and bounded ordinals;
- the vector extension via CREATE EXTENSION IF NOT EXISTS vector.

## Privacy and Retention

Semantic text and metadata exclude passwords, tokens, sessions, CSRF values,
security/audit records, credentials, arbitrary JSON, email addresses, dates of
birth, internal account identifiers, and unapproved biography/free text. Raw
vectors are retained only in the protected database table and never returned by
normal service/HTTP responses. Derived rows are disposable and can be rebuilt
from authoritative source state.
