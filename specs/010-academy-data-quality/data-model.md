# Academy Data Quality Data Model

## Persistence decision

The initial release adds no database tables, columns, indexes, or migrations.
Quality rules, findings, summaries, and remediation commands are transient
typed objects created during one request. Existing academy records remain the
only source of truth.

## Existing source entities

| Entity | Existing source | Quality relationships used |
| --- | --- | --- |
| Player | `backend/src/models/player.py` | `is_active`, normalized identity fields, and player-to-team memberships. |
| Team | `backend/src/models/team.py` | `name`, `age_group`, `version_number`, roster counts, coach coverage. |
| TeamPlayer | `backend/src/models/team_player.py` | Composite team/player membership, persisted `roster_order`, membership version. |
| User/coach | `backend/src/models/user.py` | `role`, `is_active`, `version_number`, team assignments. |
| TeamCoach | `backend/src/models/team_coach.py` | Composite team/user assignment and invalid-role detection. |
| CalendarEvent | `backend/src/models/calendar.py` | Owning event and `first_date`; current scopes are read only for semantic context. |
| RecurrenceSeries | `backend/src/models/calendar.py` | Frequency, termination, end date/count, event relationship. |
| OccurrenceException | `backend/src/models/calendar.py` | Original date, deletion/replacement state, owning series, scopes. |
| BusinessAuditEvent | `backend/src/models/business_audit_event.py` | Existing immutable mutation audit output; never a scan finding source. |

Existing foreign keys, enum checks, uniqueness constraints, and service
validation remain authoritative. Quality rules focus on lifecycle and
cross-record states that can exist despite those protections.

## Transient quality objects

### QualityRule

An immutable registry entry, not a persisted model.

| Field | Type/values | Meaning |
| --- | --- | --- |
| `rule_id` | stable string | API identity, for example `coach.inactive_assigned`. |
| `domain` | `Players`, `Teams`, `Rosters`, `Coaches`, `Calendar` | Filter and summary category. |
| `severity` | `Critical`, `Warning`, `Info` | Fixed rule severity. |
| evaluator | typed callable | Consumes the shared evaluation context and yields findings. |
| remediation policy | navigate/direct/manual | Determines the allowed UI action. |

The registry is the only allowlist for rule filters and direct actions. A
request cannot supply a callable, SQL expression, or arbitrary rule name for
execution.

### DataQualityFinding

One current violation generated by a rule.

| Field | Type/constraint | Meaning |
| --- | --- | --- |
| `finding_id` | stable string | Derived from `rule_id` plus sorted affected identifiers; independent of query order. |
| `rule_id` | registered rule ID | Rule that explains the condition. |
| `severity` | severity enum | Critical, Warning, or Info. |
| `domain` | domain enum | Players, Teams, Rosters, Coaches, or Calendar. |
| `entity_type` | typed entity label | Affected player, team, roster, coach, assignment, calendar event, series, or academy invariant. |
| `entity_id` | UUID or null | Primary affected record when one exists; null for an academy-level invariant with no unique record. |
| `entity_label` | bounded string | Human-readable label shown to the Head Coach. |
| `title` | bounded string | Concise issue title. |
| `explanation` | bounded string | Plain-language condition and why it matters. |
| `recommended_action` | bounded string | Existing workflow or safe direct action. |
| `direct_remediation` | optional typed metadata | Action name and exact target/version context, or null. |
| `related_entities` | ordered list | Stable IDs, types, and labels needed to explain cross-record findings. |

`direct_remediation` is present only for the three allowlisted action kinds and
only when current preconditions make the action eligible. The sole Head Coach
integrity finding never includes a direct action.

### QualitySummary

Calculated from the same current evaluation as the findings page.

```text
total_findings: non-negative integer
critical_count: non-negative integer
warning_count: non-negative integer
info_count: non-negative integer
domain_counts: map[Domain, non-negative integer]
```

The summary is unfiltered for every findings response. Domain keys with zero
findings may be omitted or returned as zero consistently; the contract will use
stable known domain keys for the initial release.

### DataQualityPage

The bounded read result combines the filtered page with current summary data.

```text
findings: list[DataQualityFinding]          # at most page_size
summary: QualitySummary                     # unfiltered
page: integer >= 1
page_size: integer 1..100, default 20
total_findings: integer                     # filtered total
total_pages: integer >= 0
has_previous: boolean
has_next: boolean
```

`total_pages` is zero for an empty result, matching the existing audit and
pagination response convention. The response never returns more than 100
findings.

### RemediationCommand

A discriminated, typed request for exactly one normal business mutation.

```text
NormalizeRosterOrderCommand:
  finding_id
  action = "normalize_roster_order"
  team_id
  expected_team_version >= 1
  confirmed = true

RemoveInactivePlayerCommand:
  finding_id
  action = "remove_inactive_player"
  team_id
  player_id
  expected_team_version >= 1
  confirmed = true

RemoveInactiveAssistantAssignmentCommand:
  finding_id
  action = "remove_inactive_assistant_assignment"
  coach_id
  team_id
  expected_coach_version >= 1
  confirmed = true
```

The request does not contain a generic entity ID map or arbitrary fields. The
backend re-evaluates the finding and all target conditions inside the domain
transaction before applying the change.

### RemediationResult

```text
status: "applied"
action: allowlisted action name
message: user-safe result text
affected_entity_id: UUID
audit_action: existing AuditActionType value
```

Failures use existing API error conventions. A stale version, missing target,
changed role/status, or resolved finding produces a conflict/recovery response
without a partial domain change or audit event.

## Evaluation projections

The service loads projections rather than ORM graphs:

### Player projection

```text
player_id, first_name, last_name, date_of_birth, is_active
team_id, roster_order                         # nullable for outer-join result
```

Use grouped/outer-joined results for active-unassigned and inactive-rostered
checks. Use a normalized identity projection for duplicate grouping.

### Team/roster projection

```text
team_id, team_name, age_group, team_version
player_id, player_is_active, roster_order
coach_assignment_count
```

Aggregate counts support roster bounds, inactive members, and no-coach checks.
One ordered membership query supports all four ordering rules without one query
per team.

### Coach projection

```text
coach_id, first_name, last_name, role, is_active, coach_version
team_id, team_name
```

The grouped result supports invalid roles, inactive Assistant Coach
assignments, active unassigned Assistants, and sole Head Coach coverage. The
coverage rule compares the count of current teams with distinct assignments
for the unique active Head Coach; it never treats ordinary Assistant Coach
assignment semantics as Head Coach semantics.

### Calendar projection

```text
event_id, event_name, first_date
series_id, frequency, termination, end_date, occurrence_count
exception_id, original_date, is_deleted, replacement_date
```

Scope rows are loaded only when needed to describe an affected calendar record.
The evaluator uses `calendar_recurrence.py` for recurrence semantics and keeps
academy-local date and daylight-saving behavior unchanged.

## Rule-specific validation and state transitions

| Rule family | Validation/transition behavior |
| --- | --- |
| Active/unassigned and inactive memberships | A finding exists only while the current join state satisfies the condition. Removing or assigning the relationship removes it on the next evaluation. |
| Normalized player duplicates | Group at least two records by normalized first name, last name, and date of birth; never merge or select a canonical player. |
| Team roster bounds | Count memberships and active-player state independently of database foreign-key validity. Direct removal is eligible only if the resulting active roster remains 7–15 and normal service validation passes. |
| Roster ordering | Report non-positive, duplicate, and gap conditions deterministically; report the general non-contiguous condition only for remaining defects. Normalize only the selected team to `1..N`. |
| Team/coach conflicts | Use age-group/name normalization and assignment joins; Navigate to Fix for subjective choices. |
| Sole Head Coach | Healthy means exactly one active Head Coach assigned to every current team. A broken invariant is one Critical manual-review finding and has no removal transition. |
| Assistant Coach assignment lifecycle | An inactive Assistant assignment can be removed one relationship at a time with OCC and audit; an active Assistant with no teams is Info and navigation-only. |
| Invalid coach role | Report the legacy cross-record mismatch as Critical review-only; do not alter role or delete the row automatically. |
| Calendar recurrence | Flag only a persisted end date before event first date and stale exceptions that no longer occur under the current rule. Existing CalendarService workflow handles corrective choices. |

## Transaction and audit relationships

Data Quality reads have no Business Audit relationship. Each successful direct
action invokes one existing domain mutation and stages exactly one existing
Business Audit Event in that transaction. Rollback removes both data and audit
event. Security/audit authorization denials remain outside this model.
